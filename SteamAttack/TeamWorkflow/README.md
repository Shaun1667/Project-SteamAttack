## 노션과의 관계 (D-058)

기획서·회의록의 **원본은 노션**에 있습니다. TeamWorkflow는 YPH가 노션 내용을 **정제해서 올리는 문서**로, AI와 개발자가 읽고 바로 파악하기 쉽게 정리한 것입니다. 개발과 AI 작업은 TeamWorkflow를 기준으로 합니다. 노션에서 새로 정해진 것은 YPH가 회의록·결정 로그로 옮깁니다.

## 정보는 한 곳에만 쓴다

| 정보 | 원본 | 나머지 문서는 |
|---|---|---|
| 그날 나눈 이야기 | `Meetings/날짜_제목.md` (작성 후 고치지 않음) | 링크만 |
| 지금 확정된 기획 내용 | `Design/분류/기능.md` | 링크만 |
| 무엇이 언제·왜 바뀌었나 | `Meetings/README.md`의 결정 로그 (`D-번호` 한 줄) | `D-번호`만 |
| 구현 방법·사용법·조작 키 | `Features/기능.md` | 링크만 |

## 기본 흐름

1. **회의 반영 (YPH)** → `Templates/회의록_템플릿.md`로 `Meetings/YYYY-MM-DD_제목.md` 작성. 결정마다 `D-번호`를 붙여 `Meetings/README.md` 결정 로그에 추가하고, `반영 기획서` 칸에 고칠 문서를 적는다. 기획안 원문(`Design/_원문/`)에서 나온 결정도 같은 방식으로 올린다.
2. **현황 생성** → `python Tools/check.py --write`. 담당자별 `반영 대기`가 [Meetings/현황.md](Meetings/현황.md)에 생긴다.
3. **기획서 수정 (각 구현 담당, 미정이면 NMJ)** → 자기 `반영 대기`의 결정을 회의록·최신 기획안을 보고 반영하고, 문서 `변경 이력`에 D-번호를 적는다. 담당·상태가 바뀌면 문서 머리(📌)를 고친다.
4. **구현** → 담당자가 기획서를 보고 구현한다.
5. **기능 문서** → 구현을 마치면 `Templates/기능문서_템플릿.md`로 `Features/`에 작성하고, 기획서 상태를 `완료`로 바꾼다.

## 검사와 생성

저장소의 `SteamAttack/TeamWorkflow` 폴더에서 실행합니다. 파이썬 표준 라이브러리만 씁니다.

```bash
python Tools/check.py --write
```

- 기능 표(`Design/README.md`)와 현황(`Meetings/현황.md`)을 문서 머리 정보에서 다시 만듭니다. 이 둘은 **직접 고치지 않습니다.** 병합 충돌이 나면 아무 쪽이나 고른 뒤 다시 실행하면 됩니다.
- 깨진 링크, 결정 로그에 없는 D-번호, 반영 위치가 없는 결정, 머리 정보 누락을 찾습니다. 문제가 있으면 종료 코드 1입니다.
- 커밋 전에 한 번 실행합니다. `--write` 없이 실행하면 검사만 합니다.
