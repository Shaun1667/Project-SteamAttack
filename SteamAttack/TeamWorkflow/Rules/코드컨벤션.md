# 코드 컨벤션 (Unity C#)

팀 전체가 같이 쓰는 코드 작성 규칙입니다. 사람이 쓰든 AI가 쓰든 똑같이 지킵니다.

## 1. 파일과 클래스

- 파일 하나에 클래스 하나, **파일 이름 = 클래스 이름**입니다. (Unity가 요구하는 규칙입니다.)
- **작업자 namespace** (2026-10-12 변경, 팀 빌드 ver 0.2 기준): 파일·클래스 이름에 접두사를 붙이지 않고, 클래스를 작업자 이니셜 namespace 안에 둡니다. 예: `SteamGun.cs` / `namespace YPH { public class SteamGun }`
  - namespace가 이름 겹침을 막아 줍니다. 다른 작업자 코드는 `using NGH;`로 가져오고, 같은 이름이 여러 곳에 있으면 `NGH.ObjectPool`처럼 전체 이름을 씁니다.
  - 예전 규칙(`YPH_PlayerMove.cs` / `class YPH_PlayerMove`)으로 만든 파일은 빌드 ver 0.2에서 이미 바뀌었습니다.
- 스크립트는 `Assets/Scripts/<이니셜>/` 안에만 둡니다.

## 2. 이름 짓기

| 대상 | 규칙 | 예 |
|---|---|---|
| 클래스, 구조체, enum, 메서드, 프로퍼티 | `PascalCase` | `PlayerMove`, `TakeDamage()` |
| private 필드 | `_camelCase` | `_moveSpeed` |
| 지역 변수, 매개변수 | `camelCase` | `targetPos` |
| 상수 (`const`) | `PascalCase` | `MaxHealth` |
| 인터페이스 | `I` + `PascalCase` | `IDamageable` |
| bool | 질문 형태 | `IsDead`, `_canJump` |

- 약어를 줄이지 않고 뜻이 보이게 씁니다. (`hp` 대신 `health`)
- 이벤트는 동사 과거형/현재형으로 `OnDied`, `OnHealthChanged` 처럼 씁니다.

## 3. Unity 필드 공개 방식

- 인스펙터에 보여야 하는 값은 `public` 대신 **`[SerializeField] private`** 를 씁니다.
- 다른 클래스가 읽어야 하면 프로퍼티로 공개합니다: `public int Health => _health;`
- 인스펙터 값이 많으면 `[Header("이동")]`으로 묶어서 정리합니다. 툴팁 규칙은 아래 3-1을 따릅니다.

```csharp
namespace YPH
{
    public class PlayerMove : MonoBehaviour
    {
        [Header("이동")]
        [Tooltip("캐릭터가 걷는 속도(m/초). 올리면 빨라지고, 내리면 느려집니다. 5 정도가 기본 걸음입니다.")]
        [SerializeField, Range(0f, 20f)] private float _moveSpeed = 5f;

        private Rigidbody _rigidbody;

        private void Awake()
        {
            _rigidbody = GetComponent<Rigidbody>();
        }
    }
}
```

### 3-1. 인스펙터에 보이는 값은 툴팁(Tooltip)을 한국어로 단다

인스펙터에 노출되는 값(`[SerializeField]`, `public` 필드, `ScriptableObject`의 값)은 **전부 `[Tooltip]`을 답니다.**
마우스를 올리면 설명이 나오므로, 기획자·아티스트·다른 개발자가 코드를 열지 않고도 값을 안전하게 조절할 수 있습니다.

툴팁에는 다음을 한국어로 적습니다.

1. **무엇인지** — 이 값이 무엇을 정하는지
2. **단위** — 초, m, 도(°), 배율, 개수 등
3. **올리면 / 내리면** — 수치를 바꾸면 게임에 어떤 영향이 있는지
4. **권장 범위나 주의점** — 너무 크거나 작으면 생기는 문제, 0일 때의 동작

```csharp
[Tooltip("점프 높이(m). 올리면 더 높이 뜁니다. 3 이상이면 천장을 뚫을 수 있어 주의하세요.")]
[SerializeField, Range(0.5f, 5f)] private float _jumpHeight = 1.5f;

[Tooltip("공격 사이 대기 시간(초). 내리면 공격이 빨라지고 DPS(초당 피해)가 올라갑니다. 0이면 매 프레임 공격하니 쓰지 마세요.")]
[SerializeField] private float _attackCooldown = 0.5f;

[Tooltip("체력이 0이 될 때 재생할 효과 프리팹. 비워 두면 효과 없이 사라집니다.")]
[SerializeField] private GameObject _deathEffectPrefab;
```

- 숫자 값은 가능하면 `[Range(최소, 최대)]`로 **안전한 범위**를 제한합니다. 범위를 모르면 계획서에서 정합니다.
- 오브젝트·프리팹·컴포넌트 연결 값은 **무엇을 연결하는지**와 **비워 두면 어떻게 되는지**를 적습니다.
- `bool`은 **켜면 / 끄면** 각각 어떻게 되는지 적습니다.
- 한 줄로 끝나지 않으면 두 문장까지만 씁니다. 길어지면 툴팁이 읽기 어렵습니다.
- 인스펙터에 보이지 않는 `private` 값에는 필요 없습니다. (`[HideInInspector]`로 숨긴 값도 같습니다.)
- 나쁜 예: `[Tooltip("이동 속도")]` — 이름만 되풀이하고, 올리면 어떻게 되는지 알 수 없습니다.

## 4. 성능에서 자주 하는 실수

- `GetComponent`, `Find`, `FindObjectOfType`은 `Awake`/`Start`에서 **한 번만** 하고 필드에 저장합니다. `Update`에서 반복 호출하지 않습니다.
- `Update`에서 매 프레임 `new`로 객체·배열·문자열을 만들지 않습니다. (쓰레기 수집 때문에 끊김이 생깁니다.)
- 자주 만들고 없애는 오브젝트(총알, 이펙트)는 오브젝트 풀을 씁니다.
- 태그 비교는 `tag == "Enemy"` 대신 `CompareTag("Enemy")`를 씁니다.
- 물리 처리는 `FixedUpdate`, 입력·화면 처리는 `Update`에서 합니다.

## 5. 코드 모양

- 들여쓰기는 공백 4칸, 중괄호는 새 줄에서 엽니다.
- `if`, `for` 본문이 한 줄이어도 중괄호를 씁니다.
- 한 메서드는 한 가지 일만 합니다. 길어지면(약 40줄 이상) 나눕니다.
- 접근 제한자(`private`, `public`)를 생략하지 않습니다.
- 안 쓰는 코드·주석 처리된 코드는 남기지 않고 지웁니다. (Git에 기록이 남아 있습니다.)
- 매직 넘버(`if (hp < 30)`)는 이름 있는 상수나 `[SerializeField]` 값으로 바꿉니다.

## 6. 주석

코드를 직접 짜지 않은 사람도 **주석만 읽고 코드의 흐름과 이유를 이해할 수 있게** 씁니다.
(구현은 AI가 하고, 코드를 확인하고 책임지는 사람은 개발자이기 때문입니다.)

### 6-1. 기본

- 주석은 **한국어**로 씁니다. 코드 식별자와 Unity·C# 용어는 원어 그대로 둡니다.
- 쉬운 말로 쓰되 기술적 정확성은 잃지 않습니다. 어려운 개념은 짧은 비유를 곁들입니다.
- **무엇을 하는가**와 **왜 그렇게 했는가**를 둘 다 적습니다. 코드를 봐도 이유가 안 보이는 곳이 주석이 가장 필요한 곳입니다.
- 코드를 고치면 주석도 같이 고칩니다. **틀린 주석은 없는 것보다 나쁩니다.**

### 6-2. 어디에 무엇을 쓰는가

| 위치 | 적을 내용 |
|---|---|
| **클래스 위** | 이 클래스의 **역할 한 문장**, 어떤 오브젝트에 붙이는지, 같이 쓰는 컴포넌트·연결되는 다른 클래스, 인스펙터에서 꼭 연결할 것 |
| **메서드 위** (`/// <summary>`) | 무엇을 하는지, 언제 호출되는지, 매개변수·반환값의 뜻. `private`도 포함 |
| **코드 덩어리 앞** | "이 부분은 ~를 한다" — 메서드 안의 단계 구분 (예: `// 1) 입력 읽기`, `// 2) 이동 방향 계산`) |
| **분기·반복 앞** | 왜 이 조건인지, 어떤 경우에 이 길로 오는지 |
| **계산식·숫자** | 식의 뜻과 단위. 바꾸면 어떻게 되는지 |
| **Unity·C# 개념이 어려운 곳** | `Coroutine`, `Quaternion`, `Time.deltaTime`, `event`, `LayerMask` 등이 왜 쓰였는지 한두 줄 |
| **우회·꼼수·최적화** | 왜 이렇게 했는지, 원래 방식이면 어떤 문제가 생기는지 |
| **다른 코드와의 약속** | 호출 순서, 꼭 먼저 해야 하는 초기화, 이벤트가 발생하는 시점 |

### 6-3. 예시

```csharp
namespace YPH
{
    /// <summary>
    /// 플레이어의 좌우 이동을 담당한다. (이동만 한다. 체력·공격은 다른 클래스의 일)
    /// Player 오브젝트에 붙이며, 같은 오브젝트에 Rigidbody가 있어야 한다.
    /// </summary>
    public class PlayerMove : MonoBehaviour
    {
        [Tooltip("걷는 속도(m/초). 올리면 빨라지고, 내리면 느려집니다.")]
        [SerializeField, Range(0f, 20f)] private float _moveSpeed = 5f;

        private Rigidbody _rigidbody;

        private void Awake()
        {
            // 매 프레임 GetComponent를 부르면 느리므로, 시작할 때 한 번만 찾아서 저장해 둔다.
            _rigidbody = GetComponent<Rigidbody>();
        }

        /// <summary>
        /// 입력 방향(-1 왼쪽 ~ 1 오른쪽)대로 캐릭터를 움직인다. 물리 계산 주기(FixedUpdate)마다 호출된다.
        /// </summary>
        private void Move(float direction)
        {
            // 1) 이번 물리 틱 동안 이동할 거리 = 속도 x 시간
            //    Time.fixedDeltaTime은 "한 번의 물리 계산에 걸리는 시간"이라 기기 성능과 상관없이 같은 속도가 나온다.
            float distance = _moveSpeed * direction * Time.fixedDeltaTime;

            // 2) transform을 직접 옮기면 벽을 뚫을 수 있어서, 물리 엔진(Rigidbody)에게 이동을 맡긴다.
            _rigidbody.MovePosition(_rigidbody.position + Vector3.right * distance);
        }
    }
}
```

### 6-4. 쓰지 않는 주석

- 코드를 그대로 따라 읽는 주석: `i++; // i를 1 증가` ← 이런 건 쓰지 않습니다.
- 변경 이력(`// 2026-10-01 수정`): Git에 기록이 있습니다.
- 주석 처리해 둔 옛 코드: 지웁니다.
- 줄마다 설명을 다는 것: 흐름이 한눈에 안 보입니다. **덩어리 단위**로 답니다.

### 6-5. 주석 점검

- [ ] 클래스 위에 역할 한 문장과 붙이는 곳이 적혀 있다
- [ ] 모든 메서드(`private` 포함)에 `/// <summary>`가 있다
- [ ] 메서드 안의 흐름이 단계별 주석으로 읽힌다
- [ ] "왜"가 보이지 않는 조건·숫자·우회에 이유가 적혀 있다
- [ ] 주석이 실제 코드와 일치한다

2. `[SerializeField]` 필드

4. 프로퍼티

## 8. 오류 처리

- 인스펙터에서 연결해야 하는 값이 비어 있을 수 있으면 `Awake`에서 확인하고 `Debug.LogError`로 어디가 비었는지 알립니다.
- `Debug.Log`는 개발 중에만 쓰고, 커밋 전에 불필요한 로그는 지웁니다.

## 9. 객체지향과 SOLID

모든 코드는 객체지향 4가지 특성과 SOLID 5원칙을 지켜 작성합니다.
(쉬운 말로: 코드를 **역할별 상자**로 나누고, 상자끼리는 **약속(인터페이스)** 으로만 대화하게 만드는 방법입니다.)

### 9-1. 객체지향 4가지 특성

| 특성 | 쉬운 뜻 | 이 프로젝트에서 지킬 것 |
|---|---|---|
| **캡슐화** | 내부는 숨기고 필요한 것만 보여 준다 | 필드는 `private`(또는 `[SerializeField] private`), 밖에는 프로퍼티·메서드로만 공개한다. 상태를 바꾸는 길은 메서드 하나로 모은다. |
| **추상화** | 자세한 방법은 감추고 "무엇을 하는지"만 드러낸다 | 다른 클래스가 알아야 하는 기능은 인터페이스·추상 클래스로 표현한다. (`IDamageable.TakeDamage`) |
| **상속** | 공통 부분을 부모에게 두고 자식이 이어받는다 | "A는 B **이다**"가 말이 될 때만 쓴다. 상속은 2단계까지만 하고, 기능을 붙이는 목적이면 상속 대신 **컴포넌트 조합**을 쓴다. |
| **다형성** | 같은 요청에 대상마다 다르게 반응한다 | 종류별 `if/switch` 분기 대신 인터페이스·`virtual`/`abstract`로 처리한다. |

### 9-2. SOLID 5원칙

**S — 단일 책임 (한 클래스는 한 가지 일만)**
- 클래스 설명을 "그리고" 없이 한 문장으로 말할 수 있어야 한다.
- 나쁜 예: `Player`가 이동 + 체력 + 인벤토리 + UI 갱신을 모두 한다.
- 좋은 예: `PlayerMove`, `Health`, `Inventory`, `HealthBarView`로 나누고 각각 컴포넌트로 붙인다.
- 화면 표시(View)는 게임 로직과 분리한다.

**O — 개방·폐쇄 (확장에는 열려 있고, 수정에는 닫혀 있다)**
- 새 종류(적, 무기, 스킬)를 추가할 때 **기존 코드를 고치지 않고 새 클래스만 추가**하면 되게 만든다.
- 종류가 늘어날 때마다 `switch`에 `case`를 추가해야 한다면 다형성으로 바꾼다.

**L — 리스코프 치환 (자식은 부모 자리에 들어가도 문제없어야 한다)**
- 자식 클래스가 부모의 약속(동작, 입력 조건, 결과)을 깨면 안 된다.
- 부모 메서드를 `NotImplementedException`으로 막거나, 부모 기능을 없애는 `override`를 하지 않는다. 그런 자식은 상속이 아니라는 신호이므로 구조를 다시 짠다.

**I — 인터페이스 분리 (쓰지 않는 기능을 강요하지 않는다)**
- 인터페이스는 작고 역할이 분명하게 만든다. (`IDamageable`, `IMovable` — 뚱뚱한 `ICharacter` 하나로 묶지 않는다.)
- 구현하는 쪽이 빈 메서드로 때우는 항목이 생기면 인터페이스를 쪼갠다.

**D — 의존 역전 (구체적인 것이 아니라 약속에 기대라)**
- 상위 로직은 구체 클래스(`Goblin`) 대신 인터페이스(`IDamageable`)를 바라본다.
- 필요한 대상은 클래스 안에서 `new`/`Find`로 직접 찾지 않고, 인스펙터 연결이나 `Initialize(...)` 같은 메서드로 **밖에서 넣어 준다.**
- 전역 접근(`static`, 싱글톤)은 정말 필요한 관리자 1~2개로 제한하고, 새로 늘릴 때는 계획서에 이유를 적는다.

### 9-3. Unity에서 같이 지킬 것

- **상속보다 조합**: 기능은 작은 `MonoBehaviour`를 오브젝트에 붙여 조합한다. (이동 + 체력 + 공격을 한 부모 클래스에 몰아넣지 않는다.)
- **데이터와 동작 분리**: 수치(체력, 속도, 대미지)는 `ScriptableObject`나 `[SerializeField]`로 빼서 코드를 고치지 않고 바꿀 수 있게 한다.
- **클래스끼리 직접 얽지 않기**: 다른 클래스를 알아야 할 때는 인터페이스나 C# 이벤트(`event Action`)로 연결한다. `GameObject.Find("이름")`, 문자열 `SendMessage`는 쓰지 않는다.
- **순환 참조 금지**: A가 B를 알고 B도 A를 알면 안 된다. 한쪽을 이벤트·인터페이스로 끊는다.

### 9-4. 과설계 방지

원칙은 코드를 쉽게 만들려고 지키는 것입니다. 아래는 지나친 경우입니다.

- 구현체가 하나뿐이고 앞으로 늘 계획도 없는데 인터페이스를 만든다 → 만들지 않는다.
- "나중에 필요할지도"라는 이유로 추상 클래스·팩토리·설정을 미리 만든다 → 계획서에 필요한 근거가 있을 때만 만든다.
- 규모가 작은 기능(수십 줄)을 SOLID 때문에 파일 여러 개로 쪼갠다 → 역할이 두 개 이상 섞였을 때만 나눈다.

판단 기준: **"새 종류나 변경이 실제로 예상되는 곳"** 에만 인터페이스·다형성을 쓴다.

### 9-5. 자가 점검 (구현 후 확인)

- [ ] 클래스 역할을 "그리고" 없이 한 문장으로 말할 수 있다 (S)
- [ ] 새 종류를 추가할 때 기존 `switch`/`if`를 고치지 않아도 된다 (O)
- [ ] 자식을 부모 자리에 넣어도 동작이 깨지지 않는다 (L)
- [ ] 비어 있거나 예외만 던지는 인터페이스 구현이 없다 (I)
- [ ] 구체 클래스 대신 인터페이스를 바라보고, 의존 대상을 밖에서 받는다 (D)
- [ ] public 필드가 없고, 상태 변경 경로가 메서드로 모여 있다 (캡슐화)
- [ ] 불필요한 인터페이스·추상 클래스를 만들지 않았다 (과설계 방지)

## 10. 최적화 규칙

(4번 "성능에서 자주 하는 실수"가 기본이고, 여기는 그 심화입니다.)

### 10-1. 원칙: 재고 나서 고친다

- **먼저 읽기 쉬운 코드로 만들고**, 느리다는 근거(Unity Profiler 수치, 프레임 저하 현상)가 있을 때 최적화합니다.
- 최적화한 코드에는 **왜 이렇게 했는지** 한국어 주석을 남깁니다. (예: `// 매 프레임 호출되는 경로라 할당을 피하려고 캐시함`)
- 아래 10-2~10-4의 "처음부터 지킬 것"은 근거 없이도 지킵니다. 어렵지 않고 나중에 고치기 번거롭기 때문입니다.
- 읽기 어려워질 정도의 최적화는 하지 않습니다. (9번 SOLID와 균형을 맞춥니다.)

### 10-2. 매 프레임 실행되는 곳 (`Update`, `FixedUpdate`, `LateUpdate`)

- 매 프레임 필요 없는 일은 `Update`에 두지 않습니다. 이벤트, 코루틴 간격 실행, 타이머로 바꿉니다.
- 할 일이 없는 동안은 `enabled = false`로 꺼서 `Update` 호출 자체를 막습니다.
- `Update`가 빈 메서드면 지웁니다. (비어 있어도 호출 비용이 듭니다.)
- 매 프레임 `foreach`로 큰 컬렉션을 훑지 않습니다. 필요하면 변경이 있을 때만 갱신합니다.
- 거리 비교는 `Vector3.Distance` 대신 `(a - b).sqrMagnitude`와 제곱한 기준값을 비교합니다. (제곱근 계산을 피합니다.)

### 10-3. 메모리 할당(GC) 줄이기

게임 중 쓰레기 수집(GC)이 돌면 화면이 순간적으로 멈춥니다. **자주 호출되는 코드에서 새 메모리를 만들지 않는 것**이 핵심입니다.

- 문자열 `+` 연결, `string.Format`, 보간(`$""`)을 매 프레임 쓰지 않습니다. UI 텍스트는 값이 바뀔 때만 갱신합니다.
- 자주 호출되는 곳에서 LINQ(`Where`, `Select`, `ToList` 등)를 쓰지 않습니다. `for` 루프를 씁니다.
- `new List<T>()`, `new T[]`를 반복 호출 안에서 만들지 않고 필드로 한 번 만들어 `Clear()` 하며 재사용합니다.
- 컬렉션은 크기를 알면 `new List<T>(capacity)`로 미리 잡습니다.
- 박싱(값 형식이 `object`로 변환됨)을 피합니다. `object` 매개변수, 비제네릭 컬렉션을 쓰지 않습니다.
- 자주 불리는 곳에서 람다가 바깥 변수를 붙잡으면(클로저) 매번 할당됩니다. 메서드로 빼거나 캐시합니다.
- `WaitForSeconds` 같은 yield 객체는 필드에 한 번 만들어 재사용합니다.
- 배열을 돌려주는 API는 `NonAlloc` 버전을 씁니다. (`Physics.RaycastNonAlloc`, `OverlapSphereNonAlloc`, `GetComponentsInChildren(list)` 등)

### 10-4. 호출 비용이 큰 것

- `Camera.main`, `transform`, `GetComponent<T>()` 결과는 `Awake`/`Start`에서 필드에 저장해 씁니다.
- 문자열 이름으로 찾는 것은 해시로 바꿔 미리 저장합니다: `Animator.StringToHash("Run")`, `Shader.PropertyToID("_Color")`. 매번 `animator.SetBool("Run", ...)`처럼 문자열을 넘기지 않습니다.
- `Instantiate`/`Destroy`를 자주 하지 않습니다. 반복해서 생기고 사라지는 오브젝트(총알, 이펙트, 적)는 **오브젝트 풀**을 씁니다. 풀은 각자 `Scripts/<이니셜>/` 안의 `ObjectPool`을 씁니다(D-016, 아래 12번).
- `Raycast`, `Overlap` 계열은 **레이어 마스크를 반드시 지정**하고 거리를 제한합니다. 매 프레임 필요 없으면 간격을 둡니다.
- `SendMessage`, `BroadcastMessage`, `Invoke("이름")`은 느리고 오타에 약하므로 쓰지 않습니다. 직접 호출, 이벤트, 코루틴을 씁니다.
- `Debug.Log`는 호출만 해도 비용이 듭니다. 자주 호출되는 곳에 남기지 않고, 개발용 로그는 `[System.Diagnostics.Conditional("UNITY_EDITOR")]` 메서드로 감싸 빌드에서 빠지게 합니다.

### 10-5. 물리·UI·렌더링

- 물리 객체를 움직일 때는 `Rigidbody`를 쓰고 `FixedUpdate`에서 처리합니다. 물리 객체의 `transform`을 직접 옮기지 않습니다.
- 필요 없는 충돌은 레이어 충돌 매트릭스로 끕니다. 움직이지 않는 충돌체는 `Rigidbody` 없이 둡니다.
- UI: 자주 바뀌는 요소와 거의 안 바뀌는 요소는 `Canvas`를 나눕니다. 클릭이 필요 없는 `Image`/`Text`는 `Raycast Target`을 끕니다.
- 같은 머티리얼은 공유합니다. 코드에서 `renderer.material`을 쓰면 복제본이 생기므로 값만 바꿀 때는 `MaterialPropertyBlock`이나 `sharedMaterial`을 씁니다.
- 아트·씬·프리팹 설정(텍스처 압축, 폴리곤 수, 라이트 베이크)은 코드 담당이 임의로 바꾸지 않고 담당자에게 요청합니다.

### 10-6. 목표치

- **목표 프레임: 60FPS**, **대상 플랫폼: PC**로 정했습니다.
- 60FPS는 한 프레임을 **약 16.6ms 안에** 끝내야 한다는 뜻입니다. (CPU와 GPU 모두)
- 게임 중 눈에 띄는 프레임 저하와 GC 스파이크(순간적인 멈춤)가 없어야 합니다.
- 기준 PC 사양(최소/권장 CPU·GPU·메모리)은 아직 정해지지 않았습니다. 정해지면 이 문서에 적고, 그 사양에서 프로파일링합니다.
- 모바일·콘솔은 지원하지 않으므로 해당 플랫폼 전용 최적화는 하지 않습니다.

### 10-7. 최적화 점검

- [ ] `Update` 안에 `GetComponent`/`Find`/`new`/LINQ/문자열 연결이 없다
- [ ] 반복해서 만들고 없애는 오브젝트는 풀을 쓴다
- [ ] `Raycast`/`Overlap`에 레이어 마스크와 거리 제한이 있다
- [ ] 문자열로 `Animator`·`Shader`를 매번 부르지 않고 해시를 저장해 쓴다
- [ ] 불필요한 `Debug.Log`를 지웠다
- [ ] 최적화한 곳에는 이유 주석이 있다

## 11. 협업 규칙 (코드)

여러 사람이 같은 프로젝트를 고치므로 **남에게 영향을 주는 변경은 조용히 하지 않습니다.**
Git·브랜치·씬/프리팹 규칙은 [협업규칙.md](협업규칙.md)를 따르고, 여기는 **코드를 쓸 때**의 약속입니다.

### 11-1. 내 영역과 남의 영역

- 코드는 `Scripts/<내 이니셜>/` 안에서만 만들고 고칩니다.
- 남의 코드·공용 코드에서 버그나 필요한 변경을 발견하면 **직접 고치지 않고** [요청문서_템플릿.md](../Templates/요청문서_템플릿.md)로 담당자에게 알립니다.
- 남의 코드는 **읽고 호출하는 것만** 합니다. 그 클래스의 내부(`private`)에 기대지 않습니다.

### 11-2. 다른 사람이 쓰는 코드를 바꿀 때

내가 만든 클래스를 다른 사람이 가져다 쓰고 있을 수 있습니다.

- `public` 메서드·프로퍼티·이벤트의 **이름, 매개변수, 의미**를 바꾸면 쓰는 쪽 코드가 깨집니다. 바꾸기 전에 사용하는 사람에게 알리고, 가능하면 기존 것을 남긴 채 새 것을 추가합니다.
- 없앨 코드는 먼저 `[Obsolete("대신 NewMethod를 쓰세요")]`를 붙여 알린 뒤 다음 기능 단위에서 지웁니다.
- `public` 메서드와 이벤트에는 `/// <summary>`로 **무엇을 하고, 언제 호출되는지**를 한국어로 적습니다. (남이 읽고 쓰는 설명서입니다.)

### 11-3. 직렬화 필드를 바꿀 때 (Unity에서 특히 위험)

`[SerializeField]`/`public` 필드의 **이름이나 타입을 바꾸면** 이미 프리팹·씬에 저장된 값이 사라집니다. 그 프리팹·씬은 다른 사람 것일 수 있습니다.

- 이름을 꼭 바꿔야 하면 `[FormerlySerializedAs("옛이름")]`을 붙여 값이 이어지게 합니다.
- 필드를 추가·삭제·이름 변경한 커밋은 메시지 본문에 **"직렬화 변경"** 이라고 적고, 해당 프리팹·씬 담당자에게 알립니다.
- 기본값이 필요한 새 필드는 코드의 기본값(`= 5f`)을 넣어 기존 프리팹도 안전하게 동작하게 합니다.

### 11-4. 코드끼리의 약속

- 다른 사람의 시스템과 연결할 때는 **인터페이스나 이벤트**로만 합니다. 서로의 구체 클래스를 직접 참조하지 않습니다.
- 씬 이름, 오브젝트 이름, 태그, 레이어, 경로 문자열을 코드에 흩뿌리지 않습니다. 쓸 때는 `const`로 한곳에 모읍니다.
- 전역 상태(`static`)를 새로 만들면 다른 사람 코드에 영향을 줄 수 있으므로 계획서에 이유를 적고 팀장에게 알립니다.
- 에디터 전용 코드는 `Editor` 폴더 안에 두거나 `#if UNITY_EDITOR`로 감쌉니다. 빌드가 깨지는 일을 막습니다.

### 11-5. 충돌을 줄이는 습관

- 한 파일은 작게(약 300줄 이하) 유지합니다. 한 파일을 여러 명이 건드릴 일이 줄어듭니다.
- **기능 변경과 서식 정리를 한 커밋에 섞지 않습니다.** 자동 정렬로 줄 전체가 바뀌면 다른 사람이 비교하기 어렵습니다.
- 기능 하나를 끝낼 때마다 커밋합니다. 크고 오래된 변경은 합칠 때 충돌이 큽니다.
- 커밋 전에 **컴파일 에러 0개**, 콘솔 경고 최소화를 확인합니다. 깨진 코드를 올리면 모두의 작업이 멈춥니다.
- 개인 테스트용 코드·씬·오브젝트는 커밋하지 않습니다.

### 11-6. 남기는 표시

- 나중에 할 일은 `// TODO(<이니셜>): 내용`(예: `TODO(YPH)`) 형식으로 이니셜과 함께 씁니다. 누구 일인지 알 수 있어야 합니다.
- 임시 코드는 `// TEMP(<이니셜>): 이유, 언제 지울지`로 남기고, 기능 완료 전에 정리합니다.
- 주석 처리된 옛 코드는 남기지 않습니다. (Git에 기록이 있습니다.)

### 11-7. 협업 점검

- [ ] 내 영역(`Scripts/내 이니셜`) 밖의 파일을 고치지 않았다
- [ ] `public` 인터페이스를 바꿨다면 사용하는 사람에게 알렸다
- [ ] 직렬화 필드를 바꿨다면 `FormerlySerializedAs`를 붙이고 커밋에 "직렬화 변경"을 적었다
- [ ] 컴파일 에러가 없고, 테스트용 코드·로그를 지웠다
- [ ] 기능 변경과 서식 정리를 섞지 않았다

## 12. 팀 공통 설정 (회의 결정)

팀이 정한 공통 설정입니다. 괄호 안은 결정 로그 번호입니다. 바꾸려면 새 결정을 받습니다.

### 12-1. 공통 태그 (D-013)

| Tag | 붙이는 곳 |
|---|---|
| `Player` | 플레이어 |
| `Boss` | 보스 |
| `PlayerAttack` | 플레이어 공격 콜라이더 |
| `EnemyAttack` | 적 공격 콜라이더 |
| `Enemy` | 적 |

- 태그는 프로젝트 전체 설정(`ProjectSettings/TagManager`)이라 한 사람이 바꾸면 모두의 충돌 판정이 바뀝니다. 새 태그가 필요하면 회의 안건으로 올립니다.
- 비교는 `CompareTag("Enemy")`를 씁니다(4번).

### 12-2. 오브젝트 풀링 (D-016)

- 모든 `Instantiate`는 오브젝트 풀링으로 바꿉니다. 기존 코드도 포함합니다.
- 풀은 **각자 이니셜 폴더의 `ObjectPool`** 을 씁니다. 예: `Scripts/NGH/ObjectPool.cs`. 다른 작업자의 풀을 쓸 때는 `NGH.ObjectPool`처럼 전체 이름으로 가리킵니다(1번).

### 12-3. 입력 키 (D-056)

- 게임 조작 키의 원본은 [기본조작 기획서](../Design/전투/기본조작.md)입니다. 기획서와 다른 키로 구현해야 하면 먼저 기획서 담당에게 알립니다.
- 테스트·디버그 키는 [디버깅메뉴 기획서](../Design/UI/디버깅메뉴.md)의 **키 예약표**에 먼저 등록하고 씁니다. 예약표에 있는 키는 다른 사람이 쓰지 않습니다.
- 코드에 키를 박아 넣지 않고 `[SerializeField] private Key _rewindKey = Key.Q;`처럼 인스펙터에 노출합니다. (예: `NGH.TimeRewind`)
- 디버그·테스트 키 코드는 `#if UNITY_EDITOR || DEVELOPMENT_BUILD`로 감싸 최종 빌드에서 빠지게 합니다.
