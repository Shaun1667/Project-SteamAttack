# 협업 규칙

SteamAttack 팀이 같이 지키는 Git·작업 규칙입니다.

## 1. 브랜치

- 기본은 **작업자 이니셜 브랜치**입니다. 예: `NGH`, `YPH` (현재 원격 저장소의 방식)
- 기능별로 따로 나눌 때는 `<이니셜>/기능이름`을 씁니다. 기능 이름은 영문 소문자와 `-`만 씁니다.
  - 좋은 예: `YPH/player-move`, `NGH/time-rewind`
  - 나쁜 예: `feature/player-move`(이니셜 없음), `YPH/플레이어 이동`(한글·공백)
- 기능 브랜치를 만들면 그 브랜치에는 기능 하나만 담습니다.
- **TeamWorkflow 문서 변경**(회의 반영, 기획서 수정, 요청 문서)도 코드처럼 자기 브랜치에 커밋하고, 아래 3번 흐름으로 `main`에 올립니다(D-060). 회의 반영 커밋을 올리면 NGH에게 알려 다음 병합에 넣습니다. 커밋 전에 `python Tools/check.py --write`를 실행합니다.
- `main`에는 직접 커밋하지 않습니다.

## 2. 커밋

- 아래 형식은 사람·AI 구분 없이 **모든 커밋**에 적용합니다. 지금까지 섞여 있던 형식은 그대로 두고 앞으로 지킵니다.
- **기능 하나가 끝났을 때 커밋 한 번**입니다. 작업 중간 저장용 커밋은 하지 않습니다.
- 커밋 메시지는 한국어로, 제목은 `타입: 요약` 형식이며 마침표를 붙이지 않습니다.

| 타입 | 쓰는 때 |
|---|---|
| `Init` | 프로젝트·설정의 최초 도입 |
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드·의존성·설정 등 잡무 |
| `style` | 포맷팅만 변경 |

- 성격이 다른 변경(기능 + 문서 등)은 한 커밋에 섞지 않고 나눕니다.
- 커밋할 파일은 **하나씩 직접 지정**합니다. `git add -A`, `git add .`, `git commit -a`는 쓰지 않습니다.
  (남의 폴더나 Unity가 자동으로 바꾼 설정 파일이 같이 올라가는 것을 막기 위해서입니다.)

## 3. 합치기(Merge)

- 통합 흐름은 **각자 브랜치 → NGH 브랜치에서 병합·확인 → `main`에 반영** 입니다(D-054, D-060). 작업자는 자기 브랜치를 push하고 팀장 NGH에게 알립니다. NGH가 `NGH` 브랜치에 병합해 확인한 뒤 `main`에 올립니다. `main`이 팀의 최신 통합본입니다.
- 다른 사람의 최신 작업과 문서를 받으려면 `main`을 자기 브랜치에 받아옵니다(pull 또는 merge).
- 기능 표(`Design/README.md`)·현황(`Meetings/현황.md`)은 생성 파일이라 병합 충돌이 나면 아무 쪽이나 고르면 됩니다. 다음 `check.py --write` 때 다시 맞춰집니다.

## 4. 씬과 프리팹은 한 사람만

씬(`.unity`)과 프리팹(`.prefab`)은 내용이 하나의 긴 글처럼 저장되어, 두 사람이 같이 고치면 합칠 때 거의 항상 충돌이 나고 풀기도 어렵습니다.

- 씬·프리팹 하나는 **그 시점에 한 사람만 수정**합니다.
- 내 폴더(`Scenes/이니셜`, `Prefabs/이니셜`)의 파일은 내가 담당입니다.
- `Common` 폴더와 남의 폴더에 있는 씬·프리팹은 **직접 고치지 않고 담당자에게 요청**합니다.
- 담당자가 불분명하면 팀장에게 먼저 묻습니다.

## 5. 폴더와 .meta

- 작업 파일은 `Assets/<종류>/<내 이니셜>/` 아래에 둡니다.
- `.meta` 파일은 Unity가 만듭니다. 파일을 옮기거나 지울 때는 **`.meta`도 같이** 옮기거나 지웁니다. (Unity 에디터 안에서 옮기면 자동으로 처리됩니다.)
- 파일을 커밋할 때 짝이 되는 `.meta`도 같이 올립니다.

## 6. 남의 영역 수정이 필요할 때

직접 고치지 않고 [요청문서_템플릿.md](../Templates/요청문서_템플릿.md) 양식으로 요청서를 써서 담당자에게 전달합니다.

- 요청서는 `TeamWorkflow/Requests/진행/`에 만들고 커밋합니다(D-057). 처리가 끝나면 받는 사람이 상태를 고치고 `Requests/완료/`로 옮깁니다. 받는 사람에게 알리고, 처리 결과는 요청서의 처리 기록에 남깁니다.
- 열린 요청은 [현황](../Meetings/현황.md)에 받는 사람별로 모입니다.
